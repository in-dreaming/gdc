# 自研游戏数据压缩方案研究（v0.1 草案）

> 基于 docs/research 现有资料（compress1/compress2 调研、ai based 综述、游戏数据特征说明），并补充 2025–2026 最新业界进展整理而成。
> 日期：2026-06

---

## 1. 问题定义

### 1.1 数据对象（来自《游戏数据特征说明》）

| 数据类别 | 特征 | 压缩关键点 |
|:---|:---|:---|
| 大量 Object 散文件 | 结构化（文本/数值/数组字段），80% < 16KB，95% < 300KB | 小文件 → 共享字典 / batch 合并；结构化 → 字段级转换（列化、delta） |
| 二进制文件 | Mesh、音频、表格、骨骼/标签动画、avatar | 数值流（float/quat/index）→ 类型感知转换；音频本身已熵压缩 |
| 块压缩图片 | ASTC / BCn，16B 或 8B 固定块，位域错位 | 字节对齐 LZ 难压 → 需要块感知转换（BC7Prep 类）+ 可选 RDO |
| 光照数据 | 离线/实时烘焙，连续数值场，空间相关性强 | 可接受有损/近无损量化 + 平面/通道分离 |
| 网络消息 | 高频、结构化、单条很小 | 预共享字典 + 流式上下文复用，延迟优先 |
| 内存数据 | 运行期常驻/换页数据 | 实时解压（页粒度随机访问）、低内存开销 |

### 1.2 四个核心档位（多维度诉求）

| 档位 | 典型场景 | 压缩端 | 解压端 | 对标 |
|:---|:---|:---|:---|:---|
| **A 高压缩率 + 快解压** | 首包/资源包分发、安装后即用 | 离线，可以很慢 | 数百 MB/s ~ GB/s | Oodle Kraken/Leviathan、zstd-19+ |
| **B 快压 + 快解** | 构建流水线、缓存、热更打包、用户生成内容 | 数百 MB/s | GB/s 级 | zstd-1~3、Oodle Mermaid |
| **C 极限高压** | CDN 冷分发、归档、对照基线 | 不限时 | 可以较慢（仍要可用） | LZMA、kanzi -l7、Leviathan、（实验）神经压缩 |
| **D 实时解压（要求稍低）** | 运行期内存数据、按需 streaming、网络消息 | 在线轻量 | 接近 memcpy，页粒度随机访问 | LZ4、Oodle Selkie、硬件解压 |

**结论先行**：这四个档位不可能由"一个算法"满足，但可以由**一个格式框架 + 一个统一解码器 + 可替换的编码档位**满足——这正是 2025 年后业界的共识方向（OpenZL、DirectStorage 1.4 GACL、Oodle 全家桶都是这个思路）。

## 2. 资料补充：2025–2026 关键进展（新增调研）

这些是现有 compress1/compress2 文档之后发生的、对方案有直接影响的事实：

### 2.1 OpenZL（Meta，2025.10 开源）— 最重要的参照系

- 仓库 [facebook/openzl](https://github.com/facebook/openzl)，白皮书 [arXiv:2510.03203](https://arxiv.org/abs/2510.03203)，已在 Meta 生产环境大规模使用。
- 核心理念：**格式感知压缩（format-aware compression）**。用 DAG 形式把"转换（transform）→ 编解码（codec）"组织成压缩图（graph），压缩配置随码流携带，**所有格式共享一个通用解码器**。
- 提供 SDDL（数据描述语言）描述结构化数据布局，自动生成专用压缩器；带 trainer，根据样本数据自动搜索更优压缩计划。
- v0.2.0（2026.05）：自带原生 LZ codec、自动分块（约16MB chunk）、SDDL2。
- **对我们的意义**：它验证了"分类型转换 + 统一解码器"的工程可行性，且本身 BSD 类许可开源，可以直接作为基座或抄架构。我们方案里 GameCodec 设想的"四层解耦架构"，OpenZL 已经做出了通用版本——差异在于它还没有游戏数据（BCn/ASTC、动画、IL2CPP）的转换库，这正是我们的自研空间。

### 2.2 DirectStorage 1.4 + GACL（微软，2026.03）

- DirectStorage 1.4 把 **zstd 列为一等公民 codec**（CPU 与 GPU compute shader 双路径解压，GPU zstd 解压 shader 已开源），压缩率比 GDeflate 约好 2%。
- 新增 **GACL（Game Asset Conditioning Library）**：构建期对资产做预处理（conditioning），运行期解压时自动逆变换，**对 BC1/3/4/5 纹理可让 zstd 压缩效率提升至多 50%**（BC7 支持在路上）。
- **对我们的意义**：①"构建期转换 + 解压期自动逆变换"被平台方标准化了，证明该路线是行业主流；② PC 端档位 A/D 可以直接复用 GPU 解压基础设施；③ GACL 只覆盖 PC/DirectX 与部分 BCn——移动端（ASTC/ETC2）和非纹理数据仍是空白。

### 2.3 神经压缩的工程化现状

- **NVIDIA RTX NTC**（v0.9.2-beta，2026.01）：神经纹理压缩落地中。两种模式——Inference on Load（加载时转码成 BCn，零渲染开销，全 GPU 兼容，只省磁盘/下载体积）与 Inference on Sample（渲染时神经解码，省 8x VRAM，但仅高端 GPU 实用，1080p 约 0.6–0.85ms）。GTC 2026 演示 VRAM 6.5GB→970MB。
- **JPEG-AI（ISO/IEC 6048）** 2025 年成为国际标准：端到端学习图像编码进入工业标准时代。
- **ZipNN**：面向模型权重的"类型感知 + 字节分组（byte grouping）+ 熵编码"无损压缩，比 zstd 比率好 17%、速度快 62%，多线程解压可达 80GB/s。注意：它**不是神经网络推理压缩**，而是"为特定数值数据分布设计的传统管线"——这是对"AI based"路线最现实的注解。
- **通用神经无损压缩（LLM+算术编码等）**：压缩率逼近理论极限，但吞吐仍在 MB/s 量级、需要 GPU/NPU，且跨平台位精确是大坑。**结论：3 年内不适合作为我们的通用码流主路径**，只适合（a）纹理等可有损域（NTC 路线）、（b）离线档位 C 的实验分支、（c）用学习方法离线"训练压缩计划/字典"而非在线推理。

### 2.4 其他

- **zstd 1.5.7**（2025.02）：小块压缩提速 10–30%、字典压缩提速、`--patch-from`（diff 补丁）大幅提速且比率更好、`--max` 模式。小文件 + 字典场景一直在被官方持续优化。
- **Oodle Texture / BC7Prep**：RDO（有损率失真优化，存量压缩 20–50% 收益）+ BC7Prep（无损位域重排，5–15% 收益，GPU 逆变换 >180GB/s）。主机平台（PS5 Kraken、Xbox BCPack）已把"BCn 无损转换"做进硬件解压器。
- **kanzi / bzip3 / bsc**：BWT+CM 系开源高压缩器，kanzi -l7 在 silesia 上接近 xz 比率而速度好得多，可作为档位 C 的开源备选与基线。

## 3. 总体方案：GDC 统一压缩框架（建议名：GDC-Pack）

### 3.1 设计原则

1. **一个容器格式、一个解码器、多个编码档位**。档位差异体现在"转换选择 + LZ 强度 + 熵编码开关"，解码端是同一套代码（同 OpenZL/Oodle 思路），避免客户端集成 N 个库。
2. **压缩 = 类型感知转换（transform）× 通用后端（LZ + 熵编码）**。收益的大头来自转换层（GACL 证明 BCn 上有 50% 量级提升、ZipNN 证明数值流上有 17%+），而不是再造一个比 zstd 强 3% 的 LZ。
3. **后端不自研第一版**：LZ+熵编码后端直接用 zstd（档位 A/B/C）与 LZ4 风格 raw-LZ（档位 D），把人力全部投入转换层、字典体系与容器格式。等转换层收益吃满后，再评估自研后端（rANS 交织、解码表 L1 友好等 compress2 报告中的优化点）。
4. **确定性优先**：所有转换/编码在相同输入与参数下输出比特一致（diff 友好、热更补丁小），禁浮点、禁地址相关哈希（沿用 compress1 报告的三条确定性约束）。
5. **神经/学习方法只放在离线侧**：训练字典、搜索压缩计划（OpenZL trainer 思路）、纹理 NTC/RDO；运行时解码路径保持纯整数、无推理依赖。

### 3.2 架构分层

```
┌────────────────────────────────────────────────────────┐
│ 容器层 GDC-Pack：chunk 表、类型标签、字典引用、校验、寻址  │
├────────────────────────────────────────────────────────┤
│ 转换层（构建期，按数据类型路由）                          │
│  · 结构化Object: batch合并 → 字段列化 → delta/varint     │
│  · BCn/ASTC:    块位域重排(BC7Prep类) / 端点-权重分离     │
│  · Mesh/动画:   index重排、float拆字节(byte-group)、     │
│                 quat/pos 时序delta + 量化(可选有损)       │
│  · 光照:        通道分离 + 空间预测 + 量化(近无损)        │
│  · 代码/脚本:   符号化(Courgette类, 热更场景)             │
│  · 未识别:      直通                                     │
├────────────────────────────────────────────────────────┤
│ 后端层（按档位选择）                                      │
│  A: zstd-19~22 + 训练字典       （高压+快解）            │
│  B: zstd-1~3 + 训练字典         （快压+快解）            │
│  C: zstd --max / kanzi / LZMA   （极限高压，离线）        │
│  D: raw-LZ(LZ4类, 无熵编码)      （实时，页粒度）         │
├────────────────────────────────────────────────────────┤
│ 解码层（运行期，统一）                                    │
│  统一解码器 = 后端解码 + 逆变换流水线（纯整数、SIMD）       │
│  PC可选: DirectStorage GPU 解压(zstd/GDeflate)路径        │
└────────────────────────────────────────────────────────┘
```

### 3.3 各档位具体方案

#### 档位 A：高压缩率 + 快速解压（资源分发主力）

- 转换层全开 + zstd 高等级（19–22）+ 分类型训练字典。
- 纹理走"RDO（构建期，可控有损）+ 块位域重排（无损）"，对标 Oodle Texture + Kraken 组合；移动端补 ASTC 的端点/权重/分区分离转换（业界空白，自研价值最高的点之一）。
- 解压速度预算：zstd 解压 1–1.5GB/s + 逆变换（位重排/列转行/delta 还原均为 SIMD 友好的线性扫描，目标 >2GB/s），整体仍在 GB/s 量级。
- 预期收益（基于 GACL/BC7Prep/ZipNN 公开数据外推）：相对裸 zstd-19，纹理 +15~50%，数值/表格类 +15~30%，整包 +15~25%。

#### 档位 B：快压 + 快解（流水线/热更/缓存）

- 同一容器、同一转换层（转换本身都是线性扫描，构建期开销小），后端换 zstd-1~3。
- 小文件问题用两招：**batch 合并**（已有实践：10w 文件合并后几兆）+ **分类型共享字典**（zstd 字典对 <16KB 文件收益 30–50%，且 1.5.7 后字典压缩速度大幅优化）。
- 热更 diff：确定性编码 + chunk 化（CDC 或固定块）+ `--patch-from` 风格的旧版本引用窗口。zstd 1.5.7 的 patch-from 改进可直接复用。

#### 档位 C：极限高压（离线/冷数据）

- 转换层全开 + 后端取最优者（zstd --max / LZMA / kanzi -l6~7 实测择优）。
- 实验分支：神经概率模型 + rANS（只做研究基线，衡量"理论还剩多少空间"）；NTC 作为纹理的有损极限参照。
- 该档位的真正作用：为 A/B 档位提供"还差多远"的标尺，并服务 CDN 冷端。

#### 档位 D：实时解压（内存数据 / streaming / 网络消息）

- **内存数据**：raw-LZ（LZ4 格式或自研变体），固定 4–64KB 页粒度独立压缩，支持随机访问与部分解压；冷页压缩驻留、热页按需解压（解压速度对标 LZ4 的 3–5GB/s）。可选 zstd-fast 负等级做"稍高压缩率"的次档。
- **网络消息**：预共享字典（随版本下发，离线用真实消息流训练）+ 流式上下文（同一连接复用压缩上下文）。单条消息很小 → 字典是决定性因素；候选实现 zstd streaming + dictionary，对标基线为不压缩与 LZ4。
- **PC/主机**：纹理与大资产走 GPU 解压（DirectStorage 1.4 zstd / GDeflate / 主机硬件解压器），CPU 路径只处理逆变换中无法上 GPU 的部分（块位域重排可写 compute shader，参考 BC7Prep >180GB/s 的 GPU 逆变换）。

### 3.4 与"全自研 GameCodec"路线（compress1 文档）的关系

compress1 的 GameCodec 方案方向正确（数据感知、差分友好、确定性），但有两个修正建议：

1. **不要从零写 LZ+rANS 后端起步**。OpenZL/zstd 已把后端卷到极致，自研后端 6 个月可能还打不平 zstd-3 的 Pareto 曲线；而转换层每一项（ASTC 分离、float 字节分组、列化 delta）都是 2–4 周一个、收益 10–50% 的确定性工作。先转换层，后端复用，收益/风险比高一个数量级。
2. **AI 模块降级为离线工具**。compress1/2 文档中的"运行时 INT8 MLP 熵预测"路线，按 2026 年现状评估：收益 (~5-15%) 与风险（跨平台位精确、NPU 碎片化、解压速度 -20%）不成比例。学习方法用在离线侧（字典训练、压缩计划搜索、RDO/NTC）已能拿到大部分收益。

## 4. 关键技术点清单（自研价值排序）

| # | 技术点 | 预期收益 | 工作量 | 业界现状 |
|:--|:---|:---|:---|:---|
| 1 | ASTC 块感知转换（端点/权重/分区位域分离重排） | 纹理压缩率 +10~25% | 中 | **空白**（BC7Prep 只覆盖 BC7；GACL 只覆盖 BC1-5、仅 PC） |
| 2 | 结构化 Object 列化 + 分类型字典体系（含版本管理） | 小文件 +30~50% | 中 | OpenZL 有通用件，游戏 schema 适配需自研 |
| 3 | Mesh/动画数值流转换（byte-grouping、时序 delta、量化） | +15~30% | 中 | ZipNN 思路可借鉴，动画域需自研 |
| 4 | 统一容器 + 统一解码器 + 四档位封装 | 工程基础 | 中 | 参考 OpenZL frame 格式 |
| 5 | 确定性编码 + chunk 化 + patch-from 热更管线 | 补丁 -40~60% | 中 | zstd patch-from 可复用 |
| 6 | 内存页压缩驻留（raw-LZ + 页表） | 内存占用 -30~50% | 中 | 各家引擎自研，无标准件 |
| 7 | 网络消息预共享字典 + 流式上下文 | 流量 -50~70% | 小 | zstd 字典直接可用 |
| 8 | GPU 解压集成（DS1.4 / 自写逆变换 compute shader） | 加载延迟 | 中 | PC 有标准件，移动端需自研 |
| 9 | 自研 LZ+rANS 后端（L1 友好解码表、4 路交织） | 通用 +3~8% | **大** | 二期再评估 |
| 10 | 神经熵模型 / NTC 类有损神经压缩 | 纹理体积极限 | 大 | 跟踪 NTC 成熟度，三期 |

## 5. 验证计划（最小可行实验）

1. **建语料库**：从真实项目抽取各类型数据各 ≥1GB（Object 散文件、ASTC/BCn、Mesh、动画、光照、消息日志），这是一切评估的前提。
2. **基线矩阵**：lzbench 跑 zstd(1/3/9/19/--max)、LZ4、（可拿到授权则加 Oodle Kraken/Mermaid/Selkie）、kanzi，记录 比率/压速/解速/内存 四元组，按数据类型分列。
3. **转换层 A/B 实验**（每项独立可验证）：
   - ASTC 位域分离 → zstd：对照裸 zstd；
   - Object batch+列化+字典 → zstd：对照逐文件 zstd；
   - 动画 float 字节分组+delta → zstd：对照裸 zstd；
   - 复现 GACL 在 BC 纹理上的收益作为 sanity check。
4. **OpenZL 快速评估**：用 SDDL 描述 1–2 种自家结构化格式跑 trainer，确认"借基座 vs 全自研容器"的决策依据。
5. **验收门槛建议**：档位 A 整包比裸 zstd-19 小 ≥15%；档位 B 压缩 ≥300MB/s 且比 zstd-3 小 ≥10%；档位 D 解压 ≥2GB/s（移动端 ≥1GB/s）且支持页随机访问。

## 6. 风险与开放问题

- **语料代表性**：所有"预期收益"都依赖真实数据验证，纹理的 ASTC 配置（4x4/6x6/8x8、HDR 与否）会显著影响转换收益。
- **OpenZL 依赖决策**：基座选 OpenZL 可省容器/图引擎工作量，但其格式仍在演进（v1.0 前码流可能变），需要锁版本或只借架构不借格式。
- **Oodle 对照**：若项目已有 Oodle 授权，自研档位 A 的"超越线"应设为 Kraken+Oodle Texture 组合而非 zstd。
- **有损边界**：RDO/量化（纹理、光照、动画）需要美术/引擎侧定质量标准，这是压缩率收益最大的旋钮，但不是纯技术问题。
- **专利**：ANS 本体无专利风险（Duda 公开），但避免照搬 Oodle 的具体实现细节。
